Each notebook cell runs in a fresh child process, so a package imported earlier in the notebook kernel cannot mask an installation problem.

## Recovery and resource boundary

The controller chooses the furthest required checkpoint (312, 625, 937, or 1250) that fits measured preflight checkpoint size, free disk, projected time and a 2 GiB disk margin. The trainer also performs its independent host RAM and disk checks. A partial training stage records the checkpoint SHA256 and blocks dependent stages until **Kaggle Save Version** has produced a mounted output dataset with that checkpoint. The compact ZIP excludes every `.pt`, `.safetensors`, and `.bin` file while including all audited source files; its manifest lists full recovery and inference files with sizes and hashes. It does not claim the files are durably saved. The notebook preserves prepared data, completed results and checkpoints; a stale preflight pass marker is replaced only when the real preflight reruns.

The time planner uses a conservative eight-hour session budget and the preflight's three-update timing projection. Kaggle may impose a shorter limit or have slower sustained performance. The only validation of sustained T4 memory and the baseline harness is a new Kaggle execution; no local result is labeled as a GPU pass. If the real GPU preflight fails, training remains blocked. If the required checkpoint cannot fit disk or host RAM, use hardware/storage with sufficient capacity rather than changing the assignment's batch, length, precision, optimizer, or update count.
